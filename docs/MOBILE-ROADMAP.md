# Mobile Roadmap

How Panamia Club ships to the App Store and Google Play without maintaining a
second implementation of the product.

## Overview

The Android and iOS apps are a **native shell around the live deploy**. Both
stores receive a real, signed, installable app; what that app renders is
`https://panamia.club`, served by the same Worker that serves the website.

This is deliberate, and the alternative was considered and rejected. The site is
server-rendered React Server Components running on Cloudflare Workers. There is
no static bundle to package — the HTML for a page does not exist until a request
arrives. Making one would mean either giving up SSR and RSC, or forking every
screen in `app/` into a second UI. The second UI is the expensive part: it does
not fail loudly when it drifts, it just quietly becomes a worse version of the
product, and the surface split (below) would be the first thing to rot.

The native binary owns splash, offline launch, hardware back, deep links, and
store identity. The deployed React app owns product UI, including a native-only
composition of shared features: **Directory, Social, Community, Profile**.
Browser visitors keep the existing website navigation.

### Design Philosophy

1. **Shared product core** — authentication, data, maps, social capture, and
   profile/event/group detail pages are reused. The app-specific layout is web
   code, so a Worker deployment updates it without a store review.
2. **The shell is additive, never a fork** — it adds native capability around
   the web app. It must never become a place where product behaviour lives.
3. **Native detection is client-side only** — the WebView sends the same request
   a browser does, so nothing server-rendered may depend on being in the app.
4. **One app, both surfaces** — Pana Mia and Pana social are one download.
5. **Degrade to the browser** — every native-only path (deep links, in-app
   sign-in) has a working browser fallback when it is unconfigured.

## Architecture

```
┌──────────────────────────────────────────────┐
│  Native shell (Capacitor)                    │
│  ┌────────────────────────────────────────┐  │
│  │  WKWebView / Android WebView           │  │
│  │      →  https://panamia.club           │  │──── same Worker as the website
│  │      →  https://social.panamia.club    │  │
│  └────────────────────────────────────────┘  │
│  splash · offline page · back button         │
│  deep links · status bar                     │
└──────────────────────────────────────────────┘
```

| Concern                    | Lives in                                                                                               |
| -------------------------- | ------------------------------------------------------------------------------------------------------ |
| App identity (bundle ID)   | `lib/mobile/app-identity.ts`                                                                           |
| Shell configuration        | `capacitor.config.ts`                                                                                  |
| Native-layer web behaviour | `components/mobile/NativeShell.tsx`                                                                    |
| Native layout and tab UI   | `components/mobile/NativeAppLayout.tsx`, `NativeApp.tsx`, `NativeDirectory.tsx`, `NativeCommunity.tsx` |
| Native routes/view models  | `lib/mobile/app-navigation.ts`, `browse.ts`, `map-sheet.ts`                                            |
| Runtime "am I native?"     | `lib/mobile/native.ts`                                                                                 |
| Offline fallback           | `mobile/www/offline.html`                                                                              |
| Deep-link claims (site)    | `app/.well-known/assetlinks.json`, `app/.well-known/apple-app-site-association`                        |
| Deep-link claims (app)     | `mobile/android/app/src/main/AndroidManifest.xml`, `mobile/ios/App/App/App.entitlements`               |
| Generated native projects  | `mobile/android/`, `mobile/ios/`                                                                       |

### Why the native projects are committed

`mobile/android/` and `mobile/ios/` are generated by `cap add`, but they are not
disposable. Permissions, icons, associated domains, and the manifest edits below
live in them, and regenerating throws all of that away. They are committed so
those changes are reviewable in a diff like any other code. Build output and
copied web assets are ignored — Capacitor's own generated `.gitignore` files
inside each platform handle that, and the root `.gitignore` adds signing
material on top, because Capacitor's template leaves keystores **un**ignored.

### `allowNavigation` is load-bearing

The list in `capacitor.config.ts` is not a convenience. Anything not on it opens
in the system browser, outside the app's cookie store, and three things break:

1. **`*.panamia.club`** — the surface switcher links between Pana Mia and Pana
   social by absolute cross-origin URL. Without this entry, tapping "Pana
   social" ejects the member into Chrome or Safari and "one app, both surfaces"
   is not true.
2. **OAuth providers** — a sign-in that completes in an external browser sets
   the session cookie in that browser. The app comes back signed out.
3. **Stripe Checkout** — redirects back to this origin at the end.

### Native-only navigation

`NativeAppLayout` checks the injected Capacitor bridge after hydration. It
preserves the original header, page, and footer for browsers (including mobile
browsers and PWAs). Sign-in, information, admin, and mock routes remain outside
the app frame.

- **Directory** opens at the main site's `/` or `/d`. Its branded category
  picker searches real listings, events, and groups. Directory and Events retain
  separate maps/sheets; pins use actual listing or venue coordinates only.
  Online and unlocated results stay in the list. Selecting a single pin fits
  one card, and cards open the existing detail pages.
- **Social** reuses the real feed, audience filters, stories, and post composer.
  Leaving it disconnects effects, pauses playback, and resets capture widgets,
  while the timeline/filter state stays mounted.
- **Community** defaults to **Yours**: joined groups, separately labeled pending
  requests, Hosting/Going/Interested plans, and private saved events. **Discover**
  uses horizontal photo-led cards without arrows, existing event recommendations,
  public group discovery, and community-recommended directory listings.
- **Profile** links to the authenticated member's existing `/p/[screenname]`
  page, not a mock profile or the currently selected business identity.

Explicit social-host, calendar, event-discovery, group-discovery, and detail
links keep their destinations. Visited browsing panes remain mounted behind
detail pages so returning restores their state. Private queries are scoped to
the active identity, and changing accounts clears the shared query cache.

Event saves require `drizzle/0073_event_bookmarks.sql` **before deploying the
updated Worker**. They are private, profile-scoped, idempotent bookmarks, not
RSVPs: saving never changes attendance. Account deletion explicitly removes
them even when the profile is retained for content attribution. No new native
plugin or permission is needed for this layout; an already compatible app
receives it from the deployed site.

### Native regression checks

The focused data suite uses an isolated PGlite database and the real bookmark
migration; it never needs a production connection. Browser checks use real app
components with fixture API responses, including identity changes and capture
cleanup. They do not replace physical-device or live-service testing.

```powershell
node --import tsx --test tests-unit\native-app.test.ts tests-unit\events-lanes.test.ts
node --experimental-test-module-mocks --import tsx --test tests-db\native-app-data.test.ts tests-db\feed-page.test.ts tests-db\post-composer.test.ts
yarn test native-app.spec.ts --project=chromium
```

The browser command uses the repository's normal configured development server.
It covers the native/browser gate, real detail URLs, measured card visibility,
independent maps, Community, private saves, Back priority, and stopping camera
and microphone tracks when Social becomes inactive.

## Working on the apps

Everything except building and signing iOS works on Windows, macOS, or Linux.
Capacitor 8 uses Swift Package Manager instead of CocoaPods, so the iOS project
can be scaffolded and edited anywhere — but **a Mac with Xcode is required to
compile, sign, or submit it.** There is no way around that; it is Apple's
toolchain restriction, not Capacitor's.

You do not have to _own_ that Mac, though. CI builds the iOS app on a
GitHub-hosted macOS runner on every relevant change — see
[Continuous integration](#continuous-integration) below.

For iPhone/iPad device testing, signing, TestFlight, and App Store preparation,
see [iOS Device Testing and Publishing](./IOS.md). The shared native UI includes
iOS keyboard-viewport handling, safe areas, and WebView history gestures;
Android keeps its existing UI and hardware-back behavior.

```bash
yarn mobile                # build + install + launch on Android (one command)
yarn mobile:sync           # copy web assets + config into both native projects
yarn mobile:assets         # regenerate app icons + splash screens
yarn mobile:open:android   # open in Android Studio
yarn mobile:open:ios       # open in Xcode (macOS only)
yarn mobile:doctor         # check local native toolchain setup
yarn mobile:bundle:android --version-code 1 --version-name 1.0.0
```

`yarn mobile` is the one to reach for day to day. From a shell with nothing set
up it will find your JDK and Android SDK, start an emulator if no device is
attached, sync, build, install, and launch — see
[Running it on an Android emulator](#running-it-on-an-android-emulator).
For USB/wireless phone setup and Google Play publishing, see
[Android Device Testing and Publishing](./ANDROID.md).

Run `yarn mobile:sync` after any change to `capacitor.config.ts`, after adding a
Capacitor plugin, and after editing `mobile/www/`. `yarn mobile` does it for
you; pass `--no-sync` to skip it.

### Pointing the app somewhere else

The shell reads `CAPACITOR_SERVER_URL` at config time, defaulting to
production. To run the app against a local dev server:

```bash
CAPACITOR_SERVER_URL=http://192.168.1.50:3001 yarn mobile:sync
yarn mobile
```

Use the machine's LAN address, not `localhost` — on a phone or emulator
`localhost` is the device itself. Cleartext HTTP is enabled automatically when
the URL is `http://`, and disabled again as soon as it is not, so a debug
setting cannot silently survive into a release build.

### App icons and splash screens

Source images live in `mobile/assets/` and are expanded into every size both
platforms need (87 Android files, 10 iOS):

```bash
yarn mobile:assets
```

Both masters were derived from the logos already in `public/logos/`:

| Master       | Size      | Derived from                     |
| ------------ | --------- | -------------------------------- |
| `icon.png`   | 1024×1024 | `pana_mia_icon_maskable_512.png` |
| `splash.png` | 2732×2732 | `pana_mia_icon_512.png`, centred |

The icon uses the **maskable** variant on purpose. Android adaptive icons crop
to a circle or squircle and iOS rounds the corners, so an icon whose artwork
runs to the edges loses parts of the mark. The maskable variant is the same
logo already inset for exactly that.

The splash uses the edge-to-edge variant instead, because nothing crops it —
but the outer area _is_ cut off on most aspect ratios, so the logo sits in the
middle third and the rest is flat `#fff7ec`. That value is not a guess: it is
the exact background colour of the logo files, and it is repeated in
`capacitor.config.ts` for the SplashScreen and StatusBar plugins. If one is
changed without the others, a faint rectangle appears around the splash.

Two known gaps, neither blocking:

- **`icon.png` is an upscale** from a 512px master. The art is flat vector-style
  so it holds up well, but this exact image is what appears on the App Store
  listing — a true ≥1024×1024 original is worth producing.
- **There is no dark-mode splash.** It would need a logo master with a
  transparent background; the current files have cream baked in, and chroma-
  keying it out leaves cream fringing on the anti-aliased edges. Capacitor falls
  back to the light splash, which is correct but bright.

`@capacitor/assets` also insists on emitting a PWA icon set with no flag to
disable it, including a `public/manifest.webmanifest` that would risk shadowing
the dynamic per-surface manifest served from `app/manifest.webmanifest/route.ts`.
`scripts/mobile-assets.ts` deletes that output on every run, including failed
ones.

## Deep links

A tapped `panamia.club` link should open the app rather than the browser. This
requires **two** claims that must agree, and the failure mode when they do not
is silent — no error anywhere, links simply keep opening in the browser.

| Side | Android                                   | iOS                                       |
| ---- | ----------------------------------------- | ----------------------------------------- |
| Site | `/.well-known/assetlinks.json`            | `/.well-known/apple-app-site-association` |
| App  | `intent-filter android:autoVerify="true"` | `com.apple.developer.associated-domains`  |
| Key  | `ANDROID_APP_CERT_FINGERPRINTS`           | `APPLE_APP_TEAM_ID`                       |

Both routes **404 when their env var is unset**, which is the correct answer
before a signed build exists. Serving an `assetlinks.json` with zero
certificates would be worse than serving nothing: it is a cacheable assertion
that no app owns these links.

### Android setup

`ANDROID_APP_CERT_FINGERPRINTS` takes a comma-separated list of SHA-256 signing
fingerprints. **Expect at least two.** With Play App Signing, Google re-signs
the uploaded bundle with its own key, so installs from the Play Store carry the
_app signing_ certificate while internal-test and local builds carry the
_upload_ certificate. List only one and links verify for half the builds —
usually the half nobody tests, because the developer's own phone runs the other.
Both are shown in the Play Console under **Release → Setup → App signing**.

### iOS setup

`APPLE_APP_TEAM_ID` is on the Apple Developer membership page. Separately, the
**Associated Domains** capability must be enabled for the App ID in the
developer portal, or signing fails outright. The entitlements file is already
wired into the Xcode project through the `CODE_SIGN_ENTITLEMENTS` build setting;
it deliberately does not appear in the Xcode file navigator, which is normal and
does not affect signing.

`/api/*` is excluded from the association file, ahead of the `/*` catch-all,
because first match wins. Without the exclusion, a sign-in callback opened in
Safari gets yanked into the app mid-flow and the session lands in the wrong
place.

## Sign-in: native Google and in-app email links

**Google refuses to complete OAuth in an embedded WebView.** It returns
`disallowed_useragent`, by policy, and there is no configuration that turns this
off. Android now uses Google's native Credential Manager through
`@capgo/capacitor-social-login`. Its ID token and a fresh nonce are submitted by
the WebView to Better Auth's `signIn.social`, which validates the token and sets
the cookie in the app. No browser session or Firebase project is required.
`GOOGLE_CLIENT_ID` supplies the public Web client ID at runtime. Register the
package and each signing key's SHA-1 in Google Cloud; see
[Android setup](./ANDROID.md#native-google-sign-in). Rebuild and install the
native shell after adding the plugin; a website deploy alone cannot add it.

iOS and older Android builds without the plugin keep email sign-in only.
Other providers remain hidden in native apps. Enabling Google on iOS remains
separate work that must also address Sign in with Apple / guideline 4.8.

Email links requested inside the app carry `metadata.nativeApp=true`. The
email URL is `/signin/mobile`, not the API verification endpoint. App Links or
Universal Links take it into the app; otherwise a browser landing page leaves
the token untouched and offers **Open Pana Mia app**. The explicit app scheme
works without domain association, and Android's `intent://` targets
`social.pana.app` explicitly. **Continue in browser instead** is available only
as a deliberate choice. Verification occurs inside the WebView, where its
session cookie is actually useful.

`NativeShell` validates HTTPS and narrowly scoped auth-scheme links, handles
both `appUrlOpen` and `getLaunchUrl()`, and remembers only a launch fingerprint
to avoid consuming the same link again after a reload or surface crossing.
The handoff page is private/no-store and sends no referrer. Web-requested email
links are unchanged. Accounts and verified-email linking are unchanged; see
[the sign-in documentation](./SIGNIN.md#inside-the-android-and-ios-apps).

### The hydration problem, and why there is a hook for it

`isNativeApp()` reads a global the native runtime injects into the page. The
server cannot know about it — the WebView sends exactly the request a browser
sends — so branching on it during render is a hydration mismatch.

State-plus-effect fixes the mismatch and introduces a flash: every mount renders
the browser version first and corrects it a frame later. On a cold launch that
is invisible, hidden behind the splash screen, but on an in-app navigation to
`/signin` the OAuth buttons would visibly appear and vanish.

`lib/mobile/use-native-app.ts` uses `useSyncExternalStore`, which takes a
separate server snapshot and so distinguishes the two cases: it returns `false`
while hydrating, matching the server HTML, and the real value immediately on
mounts that have no server HTML to agree with. The flash only remains where it
cannot be seen.

Any future native-only UI should use this hook rather than calling
`isNativeApp()` in a component body.

## Continuous integration

`.github/workflows/mobile-build.yml` compiles both apps on every push and pull
request that touches mobile code. Its real purpose is iOS: building an iOS app
needs macOS and Xcode, and if that only happened on one person's laptop the
project would rot silently between releases. **GitHub's macOS runners are free
for public repositories**, which is what makes this free to run — no Mac to buy,
no Apple Developer account required.

| Job     | Runner          | Produces                                    |
| ------- | --------------- | ------------------------------------------- |
| Android | `ubuntu-latest` | Unsigned debug APK, uploaded as an artifact |
| iOS     | `macos-latest`  | Simulator + unsigned device Release archive (verification only) |

Neither job takes a single secret, which is deliberate — it means both run on
pull requests from forks without exposing anything. Two things make that
possible:

- **Nothing signs.** Android builds `assembleDebug`, which uses the SDK's
  auto-generated debug keystore. iOS targets a _simulator_ destination, which
  skips code signing entirely, with `CODE_SIGNING_ALLOWED=NO` as a backstop
  against the Universal Links entitlements file pulling in a profile lookup.
- **Nothing builds the website.** The apps are a WebView pointed at the live
  deploy, so `yarn build` never runs here. No database, no Cloudflare
  credentials, no environment variables.

The Android APK artifact is sideloadable, which is the quickest way for someone
with no Android toolchain to try a branch on a real phone.

### Three things CI surfaced

Worth knowing, because the first two would look like mysterious CI failures and
the third was invisible on Windows:

- **`gradlew` was committed non-executable.** Git tracks the executable bit, and
  the file arrived as mode `644`, which is invisible on Windows and fatal on a
  Linux runner. Fixed permanently with `git update-index --chmod=+x`.
- **There was no shared Xcode scheme.** Xcode puts schemes in `xcuserdata` by
  default, which is gitignored, so `xcodebuild -scheme App` had nothing to find
  on a clean checkout. `App.xcodeproj/xcshareddata/xcschemes/App.xcscheme` is now
  committed. If the iOS target is ever recreated, that file has to come back with
  it, and its `BlueprintIdentifier` must match the target's UUID in
  `project.pbxproj`.
- **Three orphaned splash images.** The first green iOS build still warned
  `The image set "Splash" has 3 unassigned children`. `@capacitor/assets`
  rewrites `Splash.imageset/Contents.json` to point at the files it generates
  but never deletes the `splash-2732x2732*.png` placeholders from the
  `cap add ios` template. Harmless to the build, but they were the most
  obviously-named files in the directory — so the intuitive way to change the
  splash screen was to edit one of them and watch nothing happen.
  `scripts/mobile-assets.ts` now deletes them after a successful generation.

### The first run

Both jobs passed on the first attempt: iOS in 2m29s, Android in 2m41s. That run
is the first time this iOS project has ever been compiled, which retired the
biggest unknown in the whole setup — the hand-authored `App.xcscheme` is
accepted by `xcodebuild`.

A passing job is not quite the same as a working app, so the iOS job also
asserts `App.app` exists on disk afterwards. `xcodebuild -quiet` exiting `0`
having compiled nothing would otherwise be indistinguishable from success. The
Android job gets the same guarantee from `if-no-files-found: error` on its APK
upload.

### What this does not do

It does not produce anything shippable. Signed releases use the separate
`android-release.yml` and `ios-release.yml` workflows, with their own credentials
and explicit publication inputs. The iOS workflow can upload to App Store Connect
for TestFlight but never publishes a public App Store version automatically.
See [Android publishing](./ANDROID.md) and [iOS publishing](./IOS.md).

## Running it on an Android emulator

The app has now been built, installed, and launched on an emulator. This
required no Mac, no device, and no dev server — `server.url` points at
`https://panamia.club`, so the emulator loads production exactly as a phone
would.

```bash
yarn mobile
```

That is the whole thing. It finds a JDK and the Android SDK, boots an emulator
if nothing is attached, syncs, builds, installs, and launches. Pass
`--avd <name>` to choose a specific emulator or `--no-sync` to skip the copy.

The one-time prerequisites are a JDK 21 and the Android command-line tools:

```powershell
winget install EclipseAdoptium.Temurin.21.JDK
android sdk install platform-tools emulator "platforms/android-36"
android emulator create medium_phone
```

Three notes for anyone repeating this. The Android command-line tools
**replaced `sdkmanager` and `avdmanager` with a single `android` CLI** in rev
23, so most tutorials are out of date: it is `android sdk install <pkg>` and
`android emulator create <profile>` now, with `/` separators rather than `;`.

**`cap run android` does not work on Windows**, which is why `yarn mobile`
drives the build itself rather than delegating. Capacitor invokes the wrapper as
the hardcoded POSIX path `./gradlew`, and the argument masking in
`@ionic/utils-subprocess` strips only `path.sep` — which is `\` on Windows. The
`./` survives into `cross-spawn` and the build dies with `'gradlew' is not
recognized`. `cap sync` is unaffected and is still delegated.

And Gradle is started as `java -jar gradle-wrapper.jar`, not via `gradlew.bat`.
Node refuses to spawn `.bat` and `.cmd` files without a shell (CVE-2024-27980),
and handing the path to a shell would mean quoting something that can contain
spaces. The wrapper scripts do nothing but locate java and run that jar, so
calling it directly is both safer and identical on every platform.

To see what the WebView actually loaded, rather than guessing from a
screenshot, attach to it over the DevTools protocol:

```powershell
adb forward tcp:9222 localabstract:webview_devtools_remote_<pid>
curl http://127.0.0.1:9222/json/list
```

That reports the live title and URL, and is how the bug below was pinned down.

### The splash screen could brick the app

The first launch sat on the splash screen forever. The app was not broken in
any way a screenshot could show: DevTools reported `readyState: complete`, the
real page title, and all nine plugins bridged. The site had loaded perfectly.
It was simply never uncovered.

The cause was `launchAutoHide: false`, which had been set deliberately so the
splash could be held until the web app signalled first paint. What that
actually did was make a JS `hide()` call the **only** exit from the splash
screen. On Android 12+ Capacitor holds the splash with
`setKeepOnScreenCondition(() -> isVisible || isHiding)`, and the timer that
would clear `isVisible` is guarded by `if (settings.isAutoHide())` — so with
auto-hide off, that timer does nothing at all. Nothing else can ever dismiss it.

That turns any failure to run one line of JavaScript into an app that shows a
logo and nothing else, forever, with no error and no way forward. The list of
things that cause it is not exotic: a deploy that predates `NativeShell`, a
hydration error, a bad release, a rollback. The emulator hit the first of those
— production had not shipped `NativeShell` yet — which is exactly how this
surfaced.

The fix is `launchAutoHide: true` with `launchShowDuration: 10000`. The fast
path is unchanged, because `NativeShell` still calls `hide()` on first paint
and still wins. The difference is that the splash now has a ceiling it cannot
exceed. Ten seconds is deliberately generous: it is a failsafe, not a target,
and it has to outlast a cold start on a bad connection, since uncovering a
blank WebView was the original concern. Verified on the emulator — the site
appears on its own at ~10s with no `hide()` call anywhere.

A total load failure is still handled separately and much faster, by
`errorPath` swapping in `mobile/www/offline.html`, which hides the splash
itself.

## Store submission

Android signing, Play-ready App Bundle generation, and optional internal-track
publishing are documented in
[Android Device Testing and Publishing](./ANDROID.md). The first Play upload is
manual so Play App Signing and the required declarations are established before
API releases begin.

### Apple guideline 4.2 ("minimum functionality")

Apple rejects apps that are "simply a repackaged website." This is the main
submission risk for this approach and is worth taking seriously — but it is not
a ban on web-backed apps, it is a bar to clear. What already helps:

- Hardware back, splash, and an offline experience that is not a browser error.
- Deep links that open the app, so the app is a real destination on the device.
- Both surfaces in one download.
- Directory-first native tabs and map/results UI, plus the shared story camera.

What would clear it decisively is native capability the browser cannot offer —
push notifications first, then camera-backed uploads and share-sheet targets.
Push is the highest-value next step for the product regardless of review.

### Apple guideline 3.2.1(vi) — donations

`/donate` collects money inside the app. Apple only permits that for an
approved nonprofit; nonprofit registration alone does not satisfy Apple's
approval process. Until approval is confirmed, the iOS app must not expose the
donation flow inside the WebView. Fundraising must remain outside the app, such
as in the system browser.

After approval, the in-app flow must offer Apple Pay, explain how donated funds
will be used, comply with applicable law, and provide donors with appropriate
tax receipts. `app/api/create-checkout-session/route.ts` sets Stripe Checkout's
`submit_type` to `donate`, and Stripe can surface Apple Pay through the existing
`card` payment method when the device and Checkout session are eligible. Those
technical details do not replace the approval, disclosure, or receipt
requirements.

The canonical production domain is moving to `panamia.club`. Complete that
migration before device and store-review testing so the app, donation return
URLs, deep links, and public disclosures consistently use the same domain.

**Current iOS behavior:** `/donate` shows an informational screen instead of a
checkout form. In-app fundraising remains disabled until Apple nonprofit approval
is documented and accurate fund-use disclosure and tax-receipt behavior are
implemented. Web and Android donation behavior is unchanged.

Apple references:

- [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)
- [Apple Pay for Donations](https://developer.apple.com/apple-pay/nonprofits/)

### Both stores

- Bundle ID / application ID is `social.pana.app`, defined once in
  `lib/mobile/app-identity.ts` and consumed by the Capacitor config and both
  association routes. It is permanent once submitted — Apple in particular does
  not allow a bundle ID to be changed or reused after first upload.
- Privacy disclosures must match what the site actually collects; see
  `docs/PRIVACY-ROADMAP.md`.
- Account deletion must be reachable from inside the app. Both stores require it
  for any app with accounts.
